WHAT THIS IS
------------

Three demo projects built around problems from billing and payment operations.
All data is synthetic and was written for the demos. No project has users or a
production deployment, and no figure below measures business impact. The
figures are test counts and measurements on synthetic data, and each project
README gives the command, machine and versions behind them.

PROJECTS: PROBLEM -> ROOT CAUSE -> SOLUTION -> EVIDENCE
-------------------------------------------------------

1) RECONCILIATION ENGINE (PYTHON, PANDAS, DUCKDB SQL)
   Problem and root cause: A ledger and a settlement file disagree. Failure
   modes it guards against (several were found in its own v1.0.0): lookups
   that do not aggregate per reference, IDs read as numbers and malformed
   amounts dropped silently.
   Solution: Text-only ingestion, money as integer cents, one-to-one join per
   reference with one status each, 7 rules, rejected-rows file, conservation
   checks, exit codes for schedulers. The same rules run in pandas and in
   DuckDB SQL.
   Evidence (synthetic data): 171 tests, 100% statement and branch coverage on
   pandas 2.3.3 and 3.1.0. Parity tests cover both engines. 1M rows per side:
   full run in 12.7 s (pandas) or 11.1 s (SQL), a single run on one desktop
   machine.

2) LLM SUPPORT DESK (PYTHON, OLLAMA, SQLITE, DOCKER)
   Problem and root cause: Free-text payment claims need decisions that follow
   policy. A model's answer is unreliable and can be injected.
   Solution: The local LLM proposes and deterministic guardrails decide, and
   they can only escalate. JSON schema whitelist, keyword fallback, SQLite
   decision log with SQL metrics, offline eval harness.
   Evidence (synthetic data): 133 tests, 99% line and branch coverage,
   prompt-injection tests. Eval on 23 labeled tickets: llama3.2:1b 13/23
   category agreement against 21/23 for the keyword fallback; 9 of 10
   must-escalate tickets escalated on the LLM path.

3) DOCUMENT LAYOUT AUTOMATOR (C#, .NET 8, WPF + CLI)
   Problem and root cause: Fixed-width files are built by hand, and one extra
   character shifts every later field. Padding without length checks causes
   silent truncation or overflow.
   Solution: Declarative layout profiles. Lines are exactly the sum of the
   field widths, and an oversized value rejects its row. Per-row errors with
   line, field and reason. The write is fail-closed and shared by the GUI and
   the CLI.
   Evidence (synthetic data): 38 xunit tests, including golden tests on the
   committed sample output. Builds with -warnaserror and 0 warnings.
